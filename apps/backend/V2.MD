# MicroBuilt v2 — Backend playbook

**How to use:** open a fresh Claude Code session at the **repo root** (`micro-built/`, the pnpm monorepo on
branch `v2` of `SteffQing/micro-built`) and paste **one stage** at a time. Every stage starts by reading **§0**.
Do stages in order. Frontend stages live in `apps/frontend/V2.MD` and depend on the backend stages named there.

**Paths** in this file are relative to `apps/backend/` unless they start with `packages/`, `apps/frontend/` or
say "repo root". Run backend commands inside `apps/backend` (`cd apps/backend && pnpm …`) or from the root as
`pnpm --filter @microbuilt/backend <script>`.

## §0 Shared context — read before every stage

### 0.1 What v2 is
`prisma/schema.prisma` is the new **contract** (already migrated to the dev DB, init migration committed).
It replaces the old `Loan/Repayment/Config` schema and the colleague's `obligations` engine (deleted models).
v2 = rewire all code onto the contract, move auth to **better-auth**, add **Sentry**, and ship the features
from the 2026-09 meeting notes. The old code on `main` is reference only; never copy its data model.

**Monorepo:** `apps/backend` (this app, `@microbuilt/backend`), `apps/frontend` (`@microbuilt/frontend`),
`packages/shared` (`@microbuilt/shared`). The shared package already exports the phone rules
(`normalizeNgPhone`, `isNigerianPhone`), the placeholder-email rules (`placeholderEmail`, `isPlaceholderEmail`,
`visibleEmail`, `PHONE_EMAIL_DOMAIN`, `SYSTEM_EMAIL_DOMAIN`) and payroll period labels (`MONTHS`, `Month`,
`periodLabel`, `parsePeriodLabel`, `toYm`, `parseYm`, `comparePeriods`, `nextPeriod`) — import them, never
re-implement them. It has no dependencies and must stay that way: better-auth lives in this app (D15), which also
publishes the frontend's typed auth client as `@microbuilt/backend/auth-client`. On a fresh checkout run
`pnpm install` at the repo root first (it also builds `packages/shared`).
better-auth agent skills live at the repo root (`better-auth-best-practices`, `email-and-password-best-practices`,
`two-factor-authentication-best-practices`) — load them in the auth stages.

### 0.2 Ground rules
- **Admin auth rules are release blockers (D2) — never skip or defer them:** (1) every admin must have 2FA enabled:
  until they do, the API answers every route except `GET /user` with 403 `{ code: 'TWO_FACTOR_SETUP_REQUIRED' }`
  (AccessGuard, Stage 4) and the frontend keeps them on the 2FA setup screen; (2) admins sign in with password + 2FA
  only: any passwordless attempt (magic link, email code, phone code, passkey) fails with 403 "Admins sign in with
  password and 2FA", shown to them. Stage 4 builds both, and Stages 4, 5 and 7 must paste output proving both.
- Commit at the end of every stage on `v2`, message starting `backend:` (or `shared:`) and explaining *why*.
  **Never** add `Co-Authored-By`, `Generated with Claude Code` or any attribution trailer (user's global rule).
  Subagents never commit.
- Backend stages edit `apps/backend/**` and, only where a stage says so, `packages/shared/**` (orchestrator only,
  and both apps must still build). Never edit `apps/frontend/**`.
- Dependencies: `pnpm --filter @microbuilt/backend add <pkg>@<exact version>`. A version used by more than one
  workspace package (better-auth family, TypeScript) goes in the `catalog:` of `pnpm-workspace.yaml` (repo root)
  and is referenced as `"catalog:"`. One lockfile, at the repo root.
- Schema changes only where a stage says so. After any migration: `pnpm db:invariants` (idempotent SQL in
  `prisma/invariants.sql`; add new raw constraints there, never only in a migration). Prisma ignores those partial
  indexes and CHECKs when diffing, so they never show up as drift.
- `.env` points at the **dev** Railway DB; never `migrate reset`, never print `.env`. Write migrations as files
  instead of `migrate dev` (which can prompt, and turns renames into drop + create): `pnpm exec prisma migrate diff
  --from-schema-datamodel <previous schema> --to-schema-datamodel prisma --script` (previous schema:
  `git show HEAD:apps/backend/prisma/schema.prisma` into a temp file) → review; make renamed tables/columns renames →
  `prisma/migrations/<UTC yyyyMMddHHmmss>_<name>/migration.sql` → `pnpm exec prisma migrate deploy` →
  `pnpm db:invariants` → `pnpm exec prisma migrate diff --from-schema-datasource prisma --to-schema-datamodel prisma
  --script` must print an empty migration.
- Money: `Prisma.Decimal` only, via `money()` (2 dp, ROUND_HALF_UP). Numbers only in response DTOs.
- **Ledger invariants** (unit-test them): `Loan.owed` and `Loan.repaid` only ever increase.
  `owed` += X ⇔ a `DISBURSED` `MicroLoan` of X is written in the same transaction.
  `repaid` += X ⇔ a `Repayment` of X (+ its `RepaymentBreakdown` rows summing to X) in the same transaction.
- Money writes never happen in `@OnEvent` listeners or fire-and-forget code. Services write inside
  `prisma.$transaction`; events/queues only for notifications, emails, documents.
- Periods: `PayrollPeriod(month, year)`, business TZ `Africa/Lagos`. API labels `"JUNE 2026"`; range query
  params are `from=YYYY-MM&to=YYYY-MM`. Create periods lazily with an upsert on `(year, month)`.
- IDs: customers `MB-xxxxx`, admins `AD-xxxxx`, loans `LN-xxxxxx` (`src/common/utils/generate-id.ts`);
  everything else uses Prisma/better-auth defaults.
- Keep existing HTTP paths when the concept survives (the FE calls them). Every response/route change is
  logged in `apps/backend/V2_API_CHANGES.md` (tracked) under the stage that made it. The FE agent reads it.
- The app **will not compile** from Stage 1 until the end of Stage 5. Scope checks per stage:
  `pnpm exec tsc --noEmit 2>&1 | grep -E "^src/(ledger|settings)/"` must be empty for the folders the stage
  owns; unit tests run anyway (`ts-jest` is `isolatedModules`). From Stage 5 on, `pnpm exec tsc --noEmit`,
  `pnpm test`, `pnpm lint`, `pnpm build` must all pass.
- No new libraries beyond those a stage names. Pin exact versions a stage gives.

### 0.4 Open decisions — defaults the agent uses unless the user edited this list
1. **Deduction cap:** `Settings.maxDeductionRate` = the largest share of a customer's net pay (`CustomerPayroll.netPay`) the monthly deduction may take, set by admins on the dashboard. After a default raises the monthly amount above `netPay × maxDeductionRate`, the system **proposes** the smallest tenure extension that brings it back under, and notifies admins; it never extends on its own. Null = check off.
2. Tenure changes: `ADMIN` and `SUPER_ADMIN` approve/reject; admins and the system propose.
3. Top-up interest = `amount × loan.interestRate × remainingMonths` (after any tenure change approved with it), spread through the monthly deduction; payments split by the ratio rule (0.5).
4. Liquidation amount ≤ outstanding at request and at approval; no interest waiver.
5. One live loan per customer, so "liquidate a loan or all" = an amount with a "pay everything" option.
6. Proof of liquidation is required on every request and uploaded by whoever creates it (customer or admin).
7. `Settings` is filled in by a super admin on the dashboard — never seeded. Until interest + management fee rates exist, loan approval/disbursement returns 409 "Set rates in Settings first"; until the penalty rate exists, closing a period returns 409.

### 0.5 Domain rules (implement exactly; all per loan, only `DISBURSED` microloans count)
```
principalBooked = Σ MicroLoan(NEW_LOAN, TOPUP)     interestBooked = Σ MicroLoan(INTEREST)
penaltyBooked   = Σ MicroLoan(PENALTY)             owed = principalBooked + interestBooked + penaltyBooked
<x>Collected    = Σ RepaymentBreakdown(<x>)        outstanding = owed − repaid
managementFee   = Σ MicroLoan(NEW_LOAN, TOPUP).amount × loan.managementFeeRate   (taken from cash, never in owed)
frozenCount     = count Deduction(status ≠ OPEN)   remainingMonths = max(1, tenure − frozenCount)
committed       = Σ expected of Deduction(AWAITING)
OPEN.expected   = remainingMonths == 1 ? money(max(0, outstanding − committed))
                                       : money(max(0, outstanding − committed) / remainingMonths)
```
- **Disburse loan** (APPROVED→DISBURSED, one tx): MicroLoan NEW_LOAN = principal; MicroLoan INTEREST =
  `principal × interestRate × tenure` (skip if 0); owed += both; `disbursementDate`; create OPEN deduction in the
  first period ≥ disbursement month whose `variationSubmittedAt` is null; `CommodityLoan.microLoanId` if asset loan; audit.
- **Disburse top-up** (MicroLoan TOPUP APPROVED→DISBURSED): apply its approved tenure change first (if any),
  INTEREST = `amount × interestRate × remainingMonths`; owed += both; `Loan.principal += amount`; refresh OPEN.
- **Allocate a payment X — ratio method** (cap X at outstanding, one tx):
  1. charges first: `penalty = min(X, penaltyBooked − penaltyCollected)`; `R = X − penalty`;
  2. split R by the loan's **booked ratio**: `interest = money(R × interestBooked / (principalBooked + interestBooked))`,
     `principal = R − interest` (e.g. ₦100,000 + ₦20,000 interest, ₦10,000 paid → ₦8,333.33 principal, ₦1,666.67 interest);
  3. clamp each part to what's left of it (`interestBooked − interestCollected`, `principalBooked − principalCollected`)
     and move any excess to the other part — so a top-up that changes the ratio never over-collects a component
     and the final payment clears both exactly.
  Write Repayment + breakdown rows (skip zeros), `repaid += applied`, refresh OPEN; if outstanding = 0 → `REPAID`,
  set the OPEN deduction's `expected = 0` (the STOP row) and open no more.
- **Refresh OPEN** = recompute the formula. Called after every change to owed/repaid/tenure, *except* on the
  deduction a payroll payment is settling (it is AWAITING, not OPEN).
- **Payroll row** (staffid → `Customer.externalId`): no customer → inflow `UNMATCHED`; no DISBURSED loan or no
  AWAITING deduction for that period → `REVIEWING`; else allocate, link `Repayment.deductionId`, deduction →
  `FULFILLED` if applied ≥ expected else `PARTIAL` (`settledAt`); inflow `SETTLED`, or `REVIEWING` if X > applied
  (overpayment to refund). Update `CustomerPayroll` from the row only for non-empty / > 0 values.
- **Close period P** (SUPER_ADMIN; needs `variationSubmittedAt`, `closedAt` null, penalty rate set): deductions whose loan
  is no longer DISBURSED or whose `expected` is 0 are settled `FULFILLED`, no penalty. For the rest (`penalizedAt`
  null, status AWAITING|PARTIAL): AWAITING → FAILED; `shortfall = expected − Σ linked repayments`; if > 0: PENALTY
  microloan `money(shortfall × Settings.penaltyRate)` (skip 0), owed +=, audit `PENALTY_APPLIED`; set `penalizedAt`;
  refresh OPEN; **cap check** (0.4-1): if OPEN.expected > cap and no PENDING change, propose
  `TenureChange(reason DEFAULT, monthsDelta = ceil(base / cap) − remainingMonths)` where `base = outstanding − committed`.
  Finally `closedAt = now`. One tx per loan, then the period update; re-running skips done rows.
- **Variation for P** (preview/generate/submit): for each loan with an OPEN deduction in P, `prior` = its latest
  non-OPEN deduction. No prior → START; `prior.expected ≠ OPEN.expected` → AMEND (`expected 0` = STOP); equal → not
  in file. Reasons (for the FE filter): NEW_LOAN (START), TOPUP / LIQUIDATION / TENURE_CHANGE / DEFAULT if such a
  top-up disbursement, liquidation repayment, approved tenure change or penalty happened since `prior.createdAt`.
  File = xlsx sheet `Payroll changes`, columns exactly: `S/NO, IPPIS NO., NAMES OF BENEFICIARIES, COMMAND,
  LOAN BALANCE, AMOUNT, TENURE, START DATE, END DATE` (balance = outstanding, tenure = remainingMonths, dates
  dd/MM/yyyy Lagos: 1st of P → last day of P + remaining − 1).
  **Submit** (SUPER_ADMIN, once; 409 if an earlier period still has OPEN deductions — submit in month order):
  upload the file to the private variations bucket (`YYYY-MM.xlsx`), then one tx: every OPEN(P) → AWAITING; for each
  still-DISBURSED loan create OPEN(P+1) (formula); set `variationSubmittedAt`, `variationFilePath`; audit.
- **Tenure change**: propose → PENDING (DB allows one PENDING per loan → 409). Approve/reject =
  `updateMany({ where: { id, status: 'PENDING' } })`; count 0 → 409 "Already decided by another admin". Approve:
  `previousTenure = tenure`, `tenure += monthsDelta` (reject if `tenure − frozenCount < 1`), refresh OPEN, audit.
  An admin may create + approve in one call (`apply: true`).
- **Liquidation**: PaymentInflow(LIQUIDATION, AWAITING, period = current Lagos month, `proofPath` required).
  Approve (SUPER_ADMIN, as in v1; tx): recheck amount ≤ outstanding → allocate (no deductionId) → `SETTLED`; reject → `REJECTED`,
  reason in the audit entry's `note`. Tenure unchanged (an admin may change it separately).
- **Repayment rate** (customer) = Σ collected on closed-period deductions / Σ expected on them × 100 (100 if none).

### 0.7 Subagent protocol (use wherever a stage says "parallel")
1. Split only by **disjoint file sets**; no two subagents edit the same file. Shared helpers are written by the
   orchestrator *before* spawning.
2. Brief each subagent with: the goal; the exact files/folders it owns ("edit nothing else"); which §0 sections to
   read; the acceptance commands it must run and paste output for; "do not commit, do not run migrations, do not
   install packages". Ask for a report: files changed, behaviour changed, commands + results, anything left undone.
3. When it returns: `git diff --stat` must only touch its files; rerun its acceptance commands yourself; read the
   diff of its riskiest file (money/auth). A failing check goes back to the same subagent (SendMessage) with the
   output — don't silently patch over it.
4. Only the orchestrator runs migrations, installs packages and commits.
